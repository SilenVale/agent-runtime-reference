## 1. 系统架构与组件职责

### 要保证的规则

- 接入层负责受理、查询和取消登记。任务持久化之后才调度，不在请求链路里执行图。
- 消息投递器只负责把已提交的 Outbox 发到 Kafka。确认不明时沿用原消息 ID 重投。消费端仍要去重。
- Worker 消费消息、取得执行权、维护租约、加载固定版本并驱动图。Worker 不做全局恢复扫描。
- 恢复扫描按状态和到期登记调度，不直接跑图，也不因为执行槽位归零就停止。
- 工具调用经过统一闸门，再出去。业务图只提出动作，不直接改执行权和终态。
- SSE 只推已提交的事件。Kubernetes 只补实例，不恢复任务。
- PostgreSQL 是任务状态的权威。业务动作是否发生，以负责该动作的业务系统为准。假写操作就是这里用来定接口的业务系统。
- Checkpoint 独立提交。Task 只登记获准的恢复引用。
- Redis 可丢，不代替租约、Checkpoint 或操作账本。Milvus 不存任务。MySQL 不是 Runtime 的必需库，只给假写操作。
- Kafka 的 offset 只表示消费位置，不证明任务或业务完成。
- 消息重投和节点重试不自动增加 epoch。只有成功取得新执行代次才增加。
- 真实业务图不进仓库。

### 准备用什么测试证明

- `接入层受理路径不执行图`
- `消息投递不改执行权和任务终态`
- `Worker不承担全局恢复扫描`
- `Redis与Milvus与MySQL不保存任务执行权`
- `offset提交不表示任务完成`
- `假业务目录不引用底座的任务表`

## 2. 持久化模型与状态机

### 要保证的规则

- 逻辑记录至少分开：Task、租约与 epoch、Stage、Checkpoint、Operation、Event、Outbox、Inbox、Approval、Artifact。会话历史不能代替任务状态、操作账本或 Checkpoint。
- Task 保存租户、请求、幂等信息、提交人、状态、固定版本、预算上限与累计消耗、输入边界、有效恢复引用、最终结果引用和终止原因。
- 租约保存 owner、lease_expires_at 和 epoch。状态提交要同时核这三项。epoch 不是图的版本号。
- 状态迁移：ACCEPTED 等待调度；RUNNING 还要看租约，不能只看状态；WAITING_USER / WAITING_HUMAN 释放执行资源，到期不能代替批准；RECONCILING 表示外部结果不明，先查询，不重做，也不直接判失败；CANCEL_REQUESTED 停止新的业务动作；SUCCEEDED、FAILED、CANCELLED 都是终态，保护覆盖这三类，不能只挡住其中一类。取消不等于外部副作用已经回到原样。
- HANDOFF 是业务可选状态。真实业务不进仓库，这一状态保留名字，假写操作不使用它。
- 接管沿用原来的运行版本和累计预算。只有成功接管才增加 epoch。
- conversation_id、task_id、thread_id 不混用。thread_id 是这一代执行权的图状态空间。
- 重建上下文不产生新的业务授权。

### 准备用什么测试证明

- `会话记录不能代替任务状态或操作账本`
- `三类终态都拒绝旧代次回写`
- `成功接管才增加epoch且预算累计保留`
- `WAITING到期不自动当成已批准`

- 列类型用文本、带时区的时间戳和精确小数。文档未写死。

## 3. 请求受理

### 要保证的规则

请求受理要保证任务不丢、不重复创建，并且同一条任务按有效的调度轮次和执行代次推进。这不表示所有任务按提交顺序执行或完成。

第一步，保存任务并返回受理结果。

- 客户端对同一请求沿用原幂等键。接入层对租户、操作者和幂等键建立联合唯一约束，并保存规范化参数摘要。同键同参返回原 task_id，同键异参返回冲突。只有第一次受理进入 T1。
- T1 同时写入：任务、幂等登记、「任务已受理」事件、一条 Outbox。提交成功返回 HTTP 202 和 task_id。接入层随后退出，这四样仍然可读。
- 任务的累计消耗从 0 开始，终止原因为空，状态为 ACCEPTED。此时没有执行者，也没有有效租约。初始 epoch 为 0。首次调度的 dispatch_seq 为 1。
- 受理事件的 event_seq 为 1。
- Outbox 生成消息 ID，dispatch_seq 为 1，expected_epoch 为 0，操作类型 START。expected_epoch 是接管前要校验的当前代次。Worker 在 T2 校验通过并成功接管之后，才把 epoch 增加为 1。
- T1 已提交但 HTTP 响应丢失时，客户端用原幂等键重试，返回原 task_id。库不可用或超过入口容量时返回错误，客户端稍后仍用原幂等键。

第二步，把调度消息发到 Kafka。

- 投递器携带原消息 ID，以 task_id 为分区键发送。Kafka 持久化确认之后，才把 Outbox 标成已发送。失败或确认超时，保留原记录，重试仍用同一个消息 ID。
- Kafka 已接收而 Outbox 尚未标记时投递器退出，重启会再发同一条消息。这条链路允许重复投递。Inbox 按逻辑消费方加上消息 ID 去掉重复。
- 用户事件 ID 和 Outbox 消息 ID 分开生成。同一次重投不换消息 ID。新的恢复调度才使用新消息 ID 和新的 dispatch_seq，并带上待接管的 expected_epoch。

第三步，Runtime 接管并确认消息。

- Worker 关闭自动提交 offset。接管前先占本地执行名额。
- T2 按逻辑消费方加上消息 ID 去重，并按 task_id 校验任务、运行版本、dispatch_seq、expected_epoch 和租约。第一次启动要求任务是 ACCEPTED，且没有有效 owner。恢复要求该状态允许恢复，且原租约已过期。租户额度的校验、占用和接管在同一笔事务里完成。
- 接管成功时，T2 原子写入 Inbox 结论、owner、新 epoch、租约期限、任务状态和对应事件。第一次启动把状态改成 RUNNING。已经处理过的同一条消息沿用原来的结论，不因为重投再开一代。终态、旧的调度轮次、或已被其他代次接管的消息，记为忽略。
- 额度暂时不够时不接管，不授予 owner，不把任务改成 RUNNING。同一笔事务写下延期调度和原消息的延期结论，释放本地名额。到期再由 Outbox 投出新的调度消息。
- 接管给的是继续处理这条任务的资格，不是把以前的写操作再做一遍的许可。
- START 把 ACCEPTED 改成 RUNNING。RECONCILE 保持 RECONCILING，先核对已发出的操作。CANCEL 保持 CANCEL_REQUESTED。调度类型必须和数据库里的当前状态一致，不能只相信消息上写的类型。
- 只有接管完成、被明确忽略，或延期结论已经原子保存，才推进该分区的 offset。offset 表示这条调度消息已经有持久化结论，不表示任务执行完成。接管成功时，执行权已经在 T2 里。
- T2 提交前进程退出，未确认的消息可以再消费。T2 已提交但 offset 还没提交，重投靠 Inbox 和代次识别。offset 已经提交之后进程退出，不靠原消息重投，而由租约到期扫描发出新的恢复消息。

第四步，读取上下文并继续。

- 成功接管后加载任务上的固定版本、预算和关联上下文。需要恢复时加载已确认的 Checkpoint，并先核对操作账本。还没有有效 Checkpoint 时，按已保存的输入和操作记录确定位置。
- 本代次的 thread_id 是 task_id 加上当前 epoch。核对和取消不进入普通业务执行。

分区约束：一个分区在同一消费组里，同一时刻只会被一个实例消费，所以分区数决定了这个消费组能同时取消息的实例上限。本地执行槽位是实例内部的名额，不是 Kafka 分区。

### 准备用什么测试证明

- `同键同参返回原任务且同键异参冲突`
- `T1同时提交任务幂等键受理事件和Outbox并返回202`
- `初始epoch为0且接管成功后才增加`
- `投递器在确认前退出会用原消息ID再投`
- `Inbox按逻辑消费方加消息ID去掉重复接管`
- `额度不足不授予owner并留下延期调度`
- `T2提交前退出允许再消费且offset已提交后改由租约恢复`

### 文档没写死的参数

- 受理入口的在途上限：64。文档未写死。
- 本地执行槽位：每个 Runtime 实例 4。文档未写死。
- 延期第一次等待 5 秒，指数退避，上限 5 分钟，次数上限 8。文档未写死。
- 幂等键结果保留 24 小时；过期键只留摘要。请求有效期 15 分钟，由服务端签发。文档未写死。
- Kafka 主题名 `runtime.schedule`，消费组名 `runtime-workers`。文档未写死。

## 4. 执行权、预算与持久化恢复点

### 要保证的规则

这一章解决四件事：谁有权提交结果，从哪里恢复，怎样避免把业务副作用做第二遍，怎样避免重试把资源耗尽。

谁有权提交：

- 每次提交都核当前执行权。字段是 owner、epoch、租约有效期。
- 续租、提交阶段结果或终态时，数据库同时核 owner、epoch 和租约。旧代次写入拒绝。时钟用数据库时钟。
- 执行权校验只能挡住运行状态回写，撤不回已经发往假写操作的请求。再试同一动作必须沿用同一个 operation_id。

从哪里继续：

- Stage 和 Checkpoint 分开提交。一边成功、一边还没有时进程可以退出。恢复不能假设两边始终同步。
- 每个 epoch 使用独立的 checkpoint 线程。Task 上只保存通过当前执行权校验的恢复引用。旧执行者事后写出的存档，不能登记成当前任务的恢复点。
- 恢复引用必须是 Task 登记过的，并且属于同一租户、同一任务和兼容的运行版本。源存档可以来自上一有效代次，不要求它的 epoch 等于新代次。
- thread_id 绑定当前执行代次，不按 task_id 直接取旧线程的最新存档。
- 图版本或状态字段不兼容时，不硬续跑，转入对账、补偿或人工处理。

避免把外部动作做第二遍：

- 已有成功回执：复用结果，跳过该节点。
- 已有 operation_id 但没有明确成败：先按原编号向假写操作查询，不直接判失败，也不直接再写。
- 接口能够按原 operation_id 幂等：用原号重试，不生成新号。
- 不能查询也不能幂等：转人工，不自动重放。
- 操作账本独立于 Checkpoint。Checkpoint 保存图状态。操作账本保存哪些业务操作已经确认完成。恢复以操作账本和业务回执为准。
- operation_id 在动作前固定。进入节点时先生成或取出稳定的 operation_id，再执行外部调用。
- 写操作走查询、决策、执行或复用。先查阶段记录、操作账本和外部系统里有没有对应实体。只有确认还没发生，并且具备幂等条件，才允许重试。
- 只读步骤可以重算。已经决定要写的分支，不能因为模型重选就换一个新标识再做一次。没有有效 Checkpoint 时，也先查计划和操作账本。

预算：

- 预算挂在 Task 上累计。不因更换 Worker、epoch 增加或 Checkpoint 恢复而清零。
- 可用额度等于总预算减去已结算，再减去已预留未结算。
- 并行调用先原子预留，再执行，再按实际结算或释放。预留、结算、释放使用稳定的 call_id。同一 reservation_id 再来，核对 call_id 和参数后复用，不再增加预留。
- 预留事务核 owner、epoch、数据库时钟下的有效租约、取消状态和剩余额度。
- 结算按 call_id 幂等。重复回执不重复扣。费用归原始调用，不要求那次调用的 epoch 仍是当前代次。
- 只有确认调用没发出、已被可靠终止且不再计费，或实际费用已经结算，才释放未用额度。失败、超时、取消或进程崩溃本身不能证明没有费用。结果未知的预留继续占着，进入核对。
- 剩余预算不够预留时，停止新调用。不能只靠图引擎的步数上限。
- 旧 Worker 不能新增花费，也不能覆盖预算。已经产生的费用不因代次失效而丢掉。核对只能结算已存在的调用，不授予执行权，也不改终态。

租约：

- 续租由 Runtime 做，业务图不做。续租周期要明显短于租约时长。
- 续租是条件更新：task_id、owner、epoch 匹配，原租约按数据库时钟仍有效，而且当前状态允许这个执行者继续。
- 条件更新没命中，视为执行权失效。停止新的调用和状态提交，不把过期租约自己续活。
- 停心跳撤不回已发出的请求，也不立刻把执行权给别人。新的执行者仍要过 T2。已发出的动作按原 operation_id 核对。

持久化提交：

- 终态由仍持有有效执行权的一方，按当前状态和业务结果提交。CANCEL_REQUESTED 可以按取消规则进入 CANCELLED。终态不能被迟到消息重新启动。

### 准备用什么测试证明

- `旧epoch提交被拒绝且数据库时钟判断租约`
- `operation_id在调用前固定且重试不换号`
- `超时后按原operation_id查询假写且不写第二次`
- `Checkpoint与操作账本分开提交`
- `预算跨接管仍累计且旧代次不能覆盖`
- `相同call_id重复结算不重复扣费`
- `结果未知的预留在进程退出后仍然占用`
- `旧线程新存档不能登记为当前恢复引用`

### 文档没写死的参数

- 租约时长 30 秒。续租周期 10 秒。文档未写死。
- 预算必须由受理请求给出上限。没给出就拒绝受理。文档未写死。
- 预留按调用的最大可能消耗计算，当作硬上限。文档未写死。
- 金额用精确小数。文档未写死。

### 读不清

第 4 章「存档落后于业务进度时如何避免重复操作」两句原句：

- 操作账本必须独立于 Checkpoint：Checkpoint 保存的是 LangGraph 的图状态；操作账本保存的是“哪些业务操作已经确认完成”。两者分开提交事务，恢复时以操作账本和业务回执为准。2315
- operation_id 必须在动作前确定：幂等键不能在每次重试时重新生成，否则下游无法识别这是同一笔业务操作。正确做法是：进入节点时先生成或取出稳定的 operation_id ，再执行外部调用。1112

## 5. 工具执行与 MCP 接入

### 要保证的规则

- 出站工具和入站任务调用都复用现有的执行权、任务和操作账本。上下文缓存和 Checkpoint 由 Runtime 访问，不交给外部工具改。
- 所有工具，不论走 MCP、普通 HTTP 还是本地函数，都进同一道闸门。
- 闸门先检查参数、主体权限、资源归属、审批、预算、取消状态和执行权，再发出调用。
- 写工具在调用前把 operation_id 写入操作账本。operation_id 是业务幂等键，不是 MCP 请求 ID。超时或断线先按原 operation_id 查询。缺幂等或查询能力时停止自动重试，转人工。
- 只读调用可以在预算内有界重试。写操作一旦结果不明，不能直接再写一遍。
- 取消请求可以尽量往下传。取消响应或连接断开，不证明业务副作用已经撤销。
- 入站只提供受理、查询、取消。长任务断开连接不自动取消。入站不能修改 Checkpoint，也不能覆盖任务状态。
- 工具发现结果不能直接变成模型可用的工具。还要过滤允许名单、主体权限、租户、契约版本，并固定到任务上的契约版本。
- 凭证来自密钥管理，不进 Prompt、Checkpoint 或工具日志。
- 连接重建不创建新的业务动作。

### 准备用什么测试证明

- `未进工具闸门的调用不能发出`
- `写工具超时按原operation_id查询且不自动重写`
- `入站断线不取消已受理任务`
- `工具发现结果未过闸门不能成为可调用工具`

### 文档没写死的参数

- 只读工具有界重试 2 次。文档未写死。
- 单次工具超时 10 秒。文档未写死。
- 假写操作不启用入站 MCP。文档未写死。

## 6. 业务动作与运行状态一致性

### 要保证的规则

- 业务动作可能已经发生，而运行状态还没写上。恢复时先确认这一笔是否存在，再决定复用、继续或转人工。
- 调用前，持有执行权的一方在 T3 提交稳定的 operation_id、参数摘要和待执行状态。提交成功才允许调用。
- 假写操作在自己的 MySQL 事务里按 operation_id 识别重复，保存结果，再返回。这是 T4，不和 PostgreSQL 一起提交。
- 超时或响应丢失时，按原 operation_id 查询，不能直接当成没发生。
- 查清之后，Runtime 核 owner、epoch 和租约，在 T5 写下操作结果、阶段、任务状态和有序事件。单个动作成功不等于整条任务成功。
- Checkpoint 的保存遵守第 4 章，不承担业务结果确认。T6 与 T5 没有固定的先后，两边可以不一致。
- operation_id 跨网络重试和接管保持不变，不每次换成新的编号。
- 参数摘要只用来发现同一动作被换了参。两次调用参数相同，也不能单靠摘要充当动作标识。
- 假写操作的 Outbox 如果要通知结果，用途是业务结果，不是 Runtime 的调度 Outbox。

### 准备用什么测试证明

- `T3提交前不允许调用假写`
- `T4成功而T5未写时按原operation_id复用结果`
- `T5与T6分开提交且图位置落后时不重做已确认的写`
- `同一定位换参数被拒绝`

### 文档没写死的参数

- 假写查询超时 3 秒。文档未写死。
- 参数摘要用规范化 JSON 的 SHA-256。文档未写死。摘要冲突只报告，不生成第二个 operation_id。

## 7. 故障接管、人工等待与取消

### 要保证的规则

- 恢复扫描发现到期后，通过 Outbox 发出恢复、核对或取消调度。Runtime 取得新的执行代次后，再按 Checkpoint 和操作账本继续。健康的执行者也可以消费恢复消息，不必等 Pod 重建。
- Kubernetes 只重启实例。恢复扫描不直接跑图。Checkpoint 恢复发生在执行权取得之后。
- 扫描按状态和到期查找，不周期扫全部历史。候选在短事务里重新核验。没有有效执行者，或租约已到期，才登记。已有有效待处理调度时，不因为旧租约过期再发一条新消息。
- RUNNING 且租约到期：没有有效调度才登记恢复。RECONCILING：查询上一次业务结果，到次数或总时限后再转人工，不把结果不明直接当成失败。CANCEL_REQUESTED：没有有效执行者时登记取消调度；已有执行者则让它继续取消。等待状态：到期不能代替批准。终态不进入恢复扫描。
- 人工等待保存审批请求、动作摘要、有效期、恢复位置和 interrupt 标识，然后释放执行权和槽位。有效输入持久化后，才登记恢复调度。
- 取消先持久化 CANCEL_REQUESTED，并禁止再发新的普通业务动作许可。已经发出的动作还要核对。取消不等于业务回滚。只有待处理动作都有了结果，并且符合终态条件，才提交 CANCELLED。
- 登记恢复调度的事务若在提交前退出，整笔回滚，不留下半截新轮次。

### 准备用什么测试证明

- `租约到期才登记恢复且已有调度时不重复登记`
- `结果不明到时限后转人工且不自动重做`
- `人工等待到期不自动批准`
- `取消不把已发出的假写当成已回滚`
- `终态任务不会被恢复扫描重新启动`

- 核对次数上限 5，核对总时限 10 分钟。文档未写死。
- 取消处理时限 2 分钟。文档未写死。

## 8. SSE 推送、重连与多副本

### 要保证的规则

- 用户可见状态和 Event 在同一笔 PostgreSQL 事务里提交。同一任务的 event_seq 按提交顺序分配。事件按 task_id 加 event_seq 唯一。
- 客户端提交最后成功处理的 event_seq。服务端发送这个游标之后的事件。任意接入层副本都可以读这些已提交事件。
- 发送成功不表示客户端已经处理，所以允许再送一次，不承诺恰好一次。
- 客户端按 task_id 加 event_seq 去重。
- 游标超出保留窗口时，返回重新同步。客户端改取一致快照和对应序号，不把已经删掉的中间进度重放一遍。
- 非法或越权游标直接拒绝，不用空结果掩盖。
- 慢连接有发送缓冲和超时。缓冲耗尽就断开。连接保活不推进业务游标。
- 不把跨进程的写入假装成一笔共同事务。别的进程要写事件，先在自己的存储里记下意图，再幂等写入 Event。

### 准备用什么测试证明

- `断线后按event_seq补读且重复投递由客户端游标去重`
- `任一接入层副本都能读到已提交事件`
- `游标超出保留窗口时要求重新同步`
- `越权游标被拒绝`

### 文档没写死的参数

- 单任务事件保留最近 1000 条，另有一条可重读的快照。文档未写死。
- 每条连接的发送缓冲 32 条，写超时 10 秒。文档未写死。

## 9. 弹性伸缩、隔离与运维

### 要保证的规则

- 接入层、消息投递、Runtime 分开部署，分开扩缩。Kubernetes 负责实例还在不在。任务接住和恢复由 Runtime 与 PostgreSQL 负责。
- Kafka 积压只说明还有没确认的调度消息。T2 之后消息就可以确认，任务仍可能执行很久。扩容还要看有效租约数、槽位、执行时长，以及 PostgreSQL、模型和工具的额度。
- 允许执行槽位缩到 0，但恢复扫描仍要能登记 Outbox。否则恢复消息无法再把容量拉起来。
- 缩容先停止新的接管，已接管的任务在租约内继续。能在宽限期内安全提交的就提交；不能的，留下恢复点和操作意图。异常退出不把已发出的调用当成没发生。
- 租户有自己的并发和额度。延期和额度退回沿用第 3 章的原子记录。
- 进入人工等待或输入等待时，先保存等待状态和恢复依据，再释放租约和槽位。
- 发布时保留存量任务要用的图和工具契约版本。
- 灾备先隔离旧入口，核对运行状态、对象引用和业务系统里已经发生的操作，再逐步放行。不能因为库恢复了就无条件重放 Kafka 或重做业务动作。

### 准备用什么测试证明

- `执行槽位为0时恢复扫描仍能登记Outbox`
- `缩容时未完成交接的任务仍可从恢复点继续`
- `单租户额度不足时不占住其他任务的接管`
- `灾备后结果不明的写不直接重做`

### 文档没写死的参数

- 退出宽限期 40 秒，长于租约 30 秒。文档未写死。
- 单租户同时接管上限 2。文档未写死。

## 10. 典型故障与恢复处理

### 要保证的规则

下面每种故障都要留下记录，并且不把任务从已经提交的状态里抹掉。

- T1 之后 HTTP 响应丢失：任务和 Outbox 还在。用原幂等键返回原任务。
- Kafka 已发送、Outbox 未标记：同一消息 ID 可能再投。Inbox 去掉重复，不回退任务状态。
- T2 之后 offset 未提交：Inbox、owner、epoch 和租约已经在。重投认得出。原执行者失联就等租约到期。
- offset 已提交、图还没启动：执行权已经在。租约到期后发新的恢复消息。
- 旧 Worker 停顿后又恢复：旧状态回写被拒绝。外部动作靠 operation_id。
- T3 之后业务还没发出：操作记录还在，状态是待执行。按原号继续，不生成新号。
- T4 成功、T5 前退出：假写结果已经在。新的执行者取得执行权后提交 T5，不把已经完成的假写再做一遍。
- T6 成功、T5 未提交：从 Task 上最后确认的恢复点继续，并先查操作账本。
- 旧代次写 Checkpoint：留在旧线程。新的执行者用自己的线程。
- 取消、审批和完成同时到达：用条件更新决定状态。后到的请求重新检查当前状态、期限和已执行的操作。
- 事件已提交、SSE 中断：任意接入层副本按游标补读。
- 补读过程中又有新事件：同一条路的下一轮继续读。
- 游标超出保留期：返回重新同步，从一致快照继续。
- 外部结果无法再核实：停止自动重试，留下核对证据，转人工。

只有确认了业务结果，并且终态条件满足，才标失败或取消。结果不明时不直接重做。
