# Agent Runtime 参考实现

这个仓库公开的是一套多业务共用的 Agent 运行契约，以及它的可运行重建。

它保证三件事：任务接住以后不丢，执行的进程换了还能从登记过的恢复点继续，已经发往外部系统的同一次动作不打第二遍。

真实业务图和真实下游不在这个仓库里。对外只保留架构、一门假的写操作接入，以及按章排列的验收。假接入用来把契约跑通，不代表某一条具体业务。

设计来源是一份 Agent Runtime 架构说明。这里用自己的话重写契约，不贴原文。

## 一句话定位

这是一套 Agent 运行底座，不是聊天产品。接入层接住任务，消息投递把调度送进 Kafka，Runtime 掌握执行权、预算、操作账本和恢复。

```text
接入层 --受理/SSE--> PostgreSQL --Outbox--> 消息投递 --> Kafka --> Runtime
                                                              |
                                                              v
                                                           假写操作
```

## 它解决什么问题

任务会丢：请求线程里直接跑图，进程一退出，受理结果就没了。

换人没法续：执行的进程没了，后来的进程不知道从哪一版执行权接着做。

外部动作会打两遍：同一次写出去的动作如果每次都换一个新编号，下游就会再做一次。

## 演示

一条命令跑完三段事故。终端里能看见受理、投递、接管、代次拒绝、按原编号查询。

```bash
scripts/demo.sh
```

输出同时写在 `docs/demo/三段演示.txt`。当前证据是终端记录。若要录屏，先在仓库根目录执行上面的命令，画面停留在这三段输出上即可，三分钟内能看完。任意一段都是「事故被接住」：同一个幂等键没有第二条任务，退出的 Worker 之后另一个 Worker 把代次往下接，同一个 `operation_id` 没有让假写写第二次。

## 架构图

```text
幂等键
  |
  v
接入层 API ---- T1 ----> PostgreSQL（任务、Outbox、Inbox、事件、预算、操作账本）
                              |                         |
                           Outbox                     SSE 按游标读已提交事件
                              v
                           消息投递 ---- Kafka 调度消息 ----> Worker
                                                              |
                                                    epoch / 租约 / call_id
                                                              |
                                                    恢复控制器（同在 Runtime 进程）
                                                              |
                                                    operation_id
                                                              v
                                                           假写操作
```

Checkpoint 按 `task_id` 加 epoch 另存，不和操作账本一起提交。

三个进程的入口分别是 `access.AccessProcess`、`dispatch.DispatchProcess`、`rt.RuntimeProcess`。Kubernetes 清单在 `deploy/kubernetes/`，一份进程一份清单。

### 标识

| 标识 | 管什么 |
| --- | --- |
| 幂等键 | 同一次提交不建第二条任务 |
| Outbox 消息 ID | 同一次调度投递，重复投递靠它去掉 |
| dispatch_seq | 第几次调度 |
| epoch | 第几代执行权，旧代次不能回写 |
| operation_id | 同一次外部副作用，重试不换新号 |
| call_id | 同一次预算预留和结算 |

运行状态在 PostgreSQL。图的 Checkpoint 只记图走到哪。操作账本另记外部动作。预算记在任务上，换执行人不清零。

## 核心行为

### 任务接住以后不丢

受理在同一笔事务里写下任务、幂等键、「任务已受理」事件和一条 Outbox，然后返回 202。事务提交之后进程退出，这四样还在。

### 执行的进程换了还能从登记过的恢复点继续

接管成功才增加 epoch。旧代次不能回写。租约到期后，Runtime 里的恢复扫描登记新的调度，另一个 Worker 再接管。图的位置按任务和代次分开保存。

### 已经发往外部系统的同一次动作不打第二遍

`operation_id` 在调用前固定。超时或响应丢失之后按原编号向假写查询。查到了就复用，不写第二次。

## 取舍

Checkpoint 和操作账本分成两本账，是因为图走到哪，和外部动作有没有做成，不是同一件事。两边可以各提交成功一次。恢复时以操作账本和假写的回执为准。

消息可以重复投递，是因为 Kafka 已经收下和 Outbox 标成已发送不是一笔事务。重复投递由 Inbox 按消费组加上消息 ID 去掉，不靠“恰好一次”来保证任务只被接管一次。

## 快速开始

需要 Java 21。在仓库根目录执行：

```bash
scripts/run-all.sh
```

这条命令按章跑完全部验收，并再跑一次三段演示。只跑某一章：

```bash
scripts/run-chapter.sh 3
```

## 已知局限

真实的多条业务线、真实下游和生产容量不在这个仓库里。假写只认 `operation_id`，用来把接口定下来。

验收跑在进程内的 PostgreSQL 事务模型和 Kafka 日志上，用来把事务边界、重复投递和手动提交位移跑通。它不是一台已安装的数据库或 Kafka 集群，也不代表生产流量。
