# 请求受理

## 要证明的规则

- 同一个幂等键、同一份参数返回原来的任务。同一把键、不同参数返回冲突，不建第二条任务。只有第一次进入受理事务。
- 受理事务同时写下任务、幂等登记、「任务已受理」事件和一条 Outbox，提交后返回 202。提交前退出，这四样都不留下。事件 ID 和消息 ID 分开生成。响应丢失后，用原键仍能取回原任务。
- 初始 epoch 为 0，没有执行者，也没有租约。接管成功后才把代次增加，并把 START 从 ACCEPTED 改成 RUNNING。同一条消息再投不增加代次。
- 投递器在 Kafka 已经收下、Outbox 还没标记已发送时退出，重启仍用原来的消息 ID 再投。
- Inbox 按逻辑消费方加上消息 ID 去掉重复接管。逻辑消费方是消费组，不是 Pod ID。
- 额度不足时不授予 owner，不改成 RUNNING，不增加 epoch。同一笔事务留下延期调度，并释放本地名额。本地名额在开事务之前占用。
- T2 提交前退出，消息可以再消费。T2 已经提交但 offset 还没提交时，重投认得出原来的结论。offset 提交之后，租约到期由恢复扫描登记新的消息 ID 和新的调度轮次，扫描本身不增加代次。已经有待处理调度时不重复登记。
