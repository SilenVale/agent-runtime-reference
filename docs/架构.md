# 架构

这个仓库公开的是一套多业务共用的 Agent 运行契约，以及它的可运行重建。

它保证三件事：任务接住以后不丢，执行的进程换了还能从登记过的恢复点继续，已经发往外部系统的同一次动作不打第二遍。

真实业务图和真实下游不在这个仓库里。这里只保留架构、一门假的写操作，以及按章排列的验收。假写操作用来把契约跑通，不代表某一条具体业务。

实现语言用 Java。接入层、消息投递、Runtime 分成三个进程。PDF 里接入层的技术名字是 FastAPI；本仓库用 Java 做同一件事：幂等受理、返回 202、按游标续传 SSE。事务边界和标识含义不改。

## 三个进程

| 进程 | 目录 | 做什么 |
| --- | --- | --- |
| 接入层 | `底座/接入层/` | 幂等受理、查询、取消登记、SSE 按游标续传 |
| 消息投递 | `底座/消息投递/` | 读已提交的 Outbox，把调度消息发到 Kafka，确认后再标记已发送 |
| Runtime | `底座/runtime/` | 执行权、预算、操作账本、恢复扫描、Worker、工具闸门 |

假写操作放在 `假业务/`，不放进这三个目录。MySQL 只做这门假写操作的库。

Kubernetes 用本地清单把这三个进程分开跑。恢复扫描写在 Runtime 进程里，不跟着 Worker 的执行槽位归零而停。Pod 重启不代替任务恢复。

任务的权威记录在 PostgreSQL。三个 Java 进程退出，都不删除已经提交的任务。

## 六个标识

六个标识各管一件事，不互相代替。

| 标识 | 管什么 | 不拿来管什么 |
| --- | --- | --- |
| 幂等键 | 同一次提交不建第二条任务 | 不表示第几次调度，也不表示外部副作用 |
| Outbox 消息 ID | 同一次调度投递。重复投递靠它，加上逻辑消费方，在 Inbox 去掉 | 不是用户进度事件的 ID，也不是 operation_id |
| dispatch_seq | 第几次调度 | 不是执行代次 |
| epoch | 第几代执行权。旧代次不能回写 | 不阻止已经发出的外部请求，也不在消息重投时自动加一 |
| operation_id | 同一次外部副作用。重试不换号 | 不是幂等键，不是 MCP 请求 ID，不是 call_id |
| call_id | 同一次预算预留、结算和释放 | 不是 operation_id |

Inbox 去重的键是逻辑消费方加上消息 ID。逻辑消费方用消费组或处理器名称，不用 Pod ID。

用户进度事件另有事件 ID，和 Outbox 消息 ID 分开生成。Kafka 消息里用来识别这一次投递的，是 Outbox 消息 ID。

## Checkpoint 与操作账本

图的位置按 `task_id` 加 epoch 单独存放。本代次目标是 `thread_id = task_id + ":epoch-" + epoch`。Checkpoint 只存图状态和执行位置。

操作账本另存外部动作：`operation_id`、动作意图、参数摘要、确认结果。两本账分开提交。恢复时以操作账本和业务回执为准，不拿 Checkpoint 证明外部动作已经完成。

## 预算

预算记在任务上。上限、已结算消耗、已预留未结算都属于这条 Task。Worker 更换、epoch 增加、Checkpoint 恢复，都不把累计清零。预留和结算使用稳定的 call_id。

## 目录

| 路径 | 放什么 | 不放什么 |
| --- | --- | --- |
| `底座/接入层/` | 受理和 SSE | 执行权、账本、假写 |
| `底座/消息投递/` | Outbox 到 Kafka | 接管、跑图、假写 |
| `底座/runtime/` | 执行权、预算、操作账本、恢复、Worker、工具闸门 | 假业务的 MySQL 表 |
| `假业务/` | 认 operation_id 的一门假写，以及按这个编号查询 | Task、epoch、租约、Checkpoint |
| `deploy/kubernetes/` | 接入层、消息投递、Runtime 三份清单 | 真实业务图 |

这一步还没有实现代码。目录边界先写在这里。实现开始之后，假业务代码只出现在 `假业务/`。

## 存储归属

| 存储 | 保存 | 不保存 |
| --- | --- | --- |
| PostgreSQL | 任务、租约、阶段、操作账本、事件、Outbox、Inbox、审批、产物引用、会话 | 不把图状态的提交和这些行合成一笔必达事务 |
| Checkpoint 存储 | 图状态。按 task_id 加 epoch 分线程 | 不存外部动作有没有做成 |
| Redis | 可丢弃的热点缓存 | 不存租约、Checkpoint、操作账本、任务 |
| 对象存储 | 附件和大型结果 | 上传未完成的对象不作持久引用 |
| Milvus | 可重建的知识索引 | 不存任务 |
| MySQL | 假写操作自己的结果 | 不是 Runtime 的库 |
| Kafka | 调度消息 | offset 不证明任务或业务完成 |

## 组件

下面每一个组件都写五件事：负责什么、存什么、核哪个标识、事务和谁一起提交、进程退出后任务还在不在。

### 接入层

- 负责什么：校验身份和参数，按幂等键受理，返回 task_id，并提供查询和取消登记。受理成功返回 HTTP 202。不在请求链路里执行图。
- 存什么：不自存任务。任务、幂等登记、受理事件和 Outbox 写在 PostgreSQL。
- 核哪个标识：幂等键，连同租户、操作者和规范化参数摘要。同键同参返回原 task_id，同键异参冲突。
- 事务和谁一起提交：T1。同一笔事务写入任务、幂等登记、「任务已受理」事件、一条 Outbox。初始 epoch 为 0，首次 dispatch_seq 为 1，expected_epoch 为 0，操作类型 START。
- 进程退出后任务还在不在：T1 已经提交，任务还在，即使接入层随后退出。T1 没提交，整笔回滚，没有任务。

### SSE

- 负责什么：按游标读取已经提交的用户可见事件，断线以后补读。发送成功不表示客户端已经处理。
- 存什么：不另存一份事件。读 PostgreSQL 里的 Event。
- 核哪个标识：task_id 和 event_seq，以及调用者对该任务的访问权。
- 事务和谁一起提交：SSE 只读已提交数据，不加入 T1 到 T6。事件本身在产生它的那笔 PostgreSQL 事务里提交。
- 进程退出后任务还在不在：接入层退出，任务还在。客户端按最后成功的 event_seq 重连。内存里的分片可以丢。

### PostgreSQL 运行库

- 负责什么：运行状态和恢复决策的权威存储。
- 存什么：Task、租约、Stage、操作账本、Event、Outbox、Inbox、Approval、Artifact 引用，以及会话和记忆。
- 核哪个标识：由每一笔事务核。库用 task_id 把这些行归到同一条任务。
- 事务和谁一起提交：T1、T2、T3、T5 以及预留、结算、恢复登记都在这里提交。图状态的 T6 不并进这些事务。假写的 T4 不并进这些事务。
- 进程退出后任务还在不在：Java 进程退出，已提交的任务还在。数据库自己未提交的事务回滚。

### 幂等登记

- 负责什么：同一次提交不建第二条任务。
- 存什么：租户、操作者、幂等键、规范化参数摘要、task_id。
- 核哪个标识：幂等键。同键还要核对参数摘要。
- 事务和谁一起提交：和 T1 里的任务、受理事件、Outbox 一起提交。
- 进程退出后任务还在不在：登记已经提交，重试仍返回原来的任务。登记没提交，则没有任务。

### Event

- 负责什么：给用户看的进度。受理进度和调度意图分开。
- 存什么：事件 ID、task_id、任务内 event_seq、类型、内容和时间。
- 核哪个标识：task_id 加 event_seq。事件 ID 不拿去重投递，也不拿去重外部副作用。
- 事务和谁一起提交：受理事件和 T1 一起。接管事件和 T2 一起。运行进度和 T5 一起。
- 进程退出后任务还在不在：已提交的事件还在，任务还在。SSE 可以补读。

### Outbox

- 负责什么：记下还没交给 Kafka 的调度意图。
- 存什么：消息 ID、task_id、dispatch_seq、expected_epoch、操作类型、主题和重试信息，以及是否已发送。
- 核哪个标识：消息 ID。同一次投递重试不换消息 ID。新的一轮调度才换新消息 ID 和新的 dispatch_seq。
- 事务和谁一起提交：受理时的 START 行和 T1 一起插入。恢复或延期产生的新行，和 Runtime 的登记事务一起插入。标记已发送是投递器在 Kafka 确认之后的另一次更新。
- 进程退出后任务还在不在：行已经提交，任务还在。投递器退出不会把任务删掉。

### 消息投递器

- 负责什么：读取已提交且待发送的 Outbox，携带原消息 ID 发到 Kafka，持久化确认后再标记已发送。
- 存什么：不存任务。只更新 Outbox 的已发送标记。
- 核哪个标识：Outbox 消息 ID。确认不明时仍用这个消息 ID 重投。
- 事务和谁一起提交：Kafka 发送和 PostgreSQL 的已发送标记不是一笔事务。不和 T2 接管写在一起。
- 进程退出后任务还在不在：任务还在。若退出发生在 Kafka 已接收、Outbox 尚未标记，重启后会再发同一条消息。

### Kafka

- 负责什么：给调度消息排队，按消费组分发给 Runtime。
- 存什么：调度消息。offset 只表示消费位置。
- 核哪个标识：消息上带着 task_id、消息 ID、dispatch_seq、expected_epoch。Kafka 自己不核执行权，也不核 operation_id。
- 事务和谁一起提交：不能和 PostgreSQL 的更新合成一笔事务。
- 进程退出后任务还在不在：任务还在 PostgreSQL。Kafka 或投递进程退出，只影响这条消息是否需要再投，不删除任务。

### Inbox

- 负责什么：认出重复投递，避免同一次调度被接管两次。
- 存什么：逻辑消费方、消息 ID、处理结论、关联的执行代次。
- 核哪个标识：逻辑消费方加上消息 ID。不用 Pod ID。
- 事务和谁一起提交：和 T2 里的 owner、新 epoch、租约、任务状态、接管事件一起提交。
- 进程退出后任务还在不在：结论已经提交，任务还在。同一条消息再来，不再启动新的执行代次。

### 租约与 epoch

- 负责什么：标明现在谁能提交，以及这是第几代执行权。
- 存什么：owner、lease_expires_at、epoch，记在这条任务的执行权上。
- 核哪个标识：提交时同时核 owner、epoch 和数据库时钟下的租约。旧 epoch 的写入拒绝。
- 事务和谁一起提交：T2 校验通过并成功接管，才把 epoch 加一，并和 Inbox、owner、租约、状态一起提交。初始 epoch 为 0。续租是之后的条件更新。
- 进程退出后任务还在不在：任务还在。进程退出不自动增加 epoch。租约到期后由恢复扫描再调度。

### Worker

- 负责什么：消费调度消息，预留本地执行名额，在 T2 取得执行权，加载任务上的固定版本，驱动图，并续租。不做全局恢复扫描。
- 存什么：不把任务只放在内存。内存中的执行进度可以丢。
- 核哪个标识：task_id、运行版本、dispatch_seq、expected_epoch、租约，以及逻辑消费方加上消息 ID。
- 事务和谁一起提交：接管用 T2。图状态不放进 T2。offset 要等 T2 提交、或明确忽略、或延期结论已经持久化之后，才按分区连续位置提交。
- 进程退出后任务还在不在：任务还在。T2 未提交，消息可以再消费。T2 已提交而 offset 未提交，重投靠 Inbox 识别。offset 已提交，则等租约到期，由新的 Outbox 恢复，不依赖原消息。

### 执行适配器

- 负责什么：把运行语义交给图引擎。校验获准的恢复引用，导入当前 epoch 的独立线程。业务图不能直接改执行权和终态。
- 存什么：不保存 owner、epoch 和调度记录。
- 核哪个标识：Task 上的有效恢复引用，以及 thread_id 必须对应当前 epoch。源存档可以来自上一有效代次。
- 事务和谁一起提交：图状态由 Checkpoint 自己的事务提交。恢复引用登记到 Task，发生在执行权校验通过之后，不和旧线程的写入合成一笔。
- 进程退出后任务还在不在：任务还在。没登记进 Task 的新存档，不能当作当前恢复点。

### 恢复控制器

- 负责什么：按任务状态和到期时间扫描，登记恢复、核对或再调度，并写 Outbox。不直接运行图，不授予 owner，不增加 epoch。
- 存什么：选主和扫描所需的到期字段。不保存业务结果。
- 核哪个标识：登记前重新读取 task_id、状态、租约和当前调度。新消息携带新的消息 ID、dispatch_seq 和 expected_epoch。
- 事务和谁一起提交：调度登记和对应 Outbox 在同一笔 PostgreSQL 事务。和 Kafka 发送分开。
- 进程退出后任务还在不在：任务还在。这个职责放在 Runtime 进程中，扫描不随执行槽位归零而停止。Runtime 进程退出后，已提交的调度还在；未提交的登记回滚。进程再起来后续扫。多个扫描重叠时，靠登记事务的条件更新避免重复登记。

### Checkpoint

- 负责什么：记下图走到哪。
- 存什么：图状态、执行位置、状态中的消息。每个 epoch 一条独立线程，键是 task_id 加 epoch。
- 核哪个标识：登记为有效恢复引用时，核当前执行权。不核 operation_id，也不凭图状态宣布外部动作完成。
- 事务和谁一起提交：T6，Checkpointer 独立提交。不和操作账本一起提交，也不和 T5 合成一笔。
- 进程退出后任务还在不在：任务还在。已经独立提交的存档还在。Worker 可以在账本和存档只成功一边时退出，恢复时不能假设两边同步。

### Stage

- 负责什么：记下哪些节点或业务步骤已经有确认结果。
- 存什么：节点、分支、结果引用和恢复输入。
- 核哪个标识：写入时核 task_id、owner、epoch 和租约。
- 事务和谁一起提交：和 T5 的任务状态、有序事件一起提交。
- 进程退出后任务还在不在：已提交的阶段记录还在，任务还在。

### 操作账本

- 负责什么：记住同一次外部副作用发没发、结果明不明。
- 存什么：operation_id、动作定位、参数摘要、待执行意图、确认结果和状态。
- 核哪个标识：operation_id。动作前就固定，重试不换号。写入前核 owner、epoch、租约和取消状态。
- 事务和谁一起提交：T3。在调用假写操作之前单独提交。不和 Checkpoint 一起提交，也不和假业务的 MySQL 事务一起提交。
- 进程退出后任务还在不在：账本行已经提交，任务还在。结果不明就按原 operation_id 查询，不把这次动作做成第二遍。

### 预算

- 负责什么：限制并累计这一条任务的消耗。
- 存什么：上限、已结算、已预留，记在 Task 上。每一笔预留另记 call_id 和 reservation_id，仍属于这个 task_id。
- 核哪个标识：call_id、reservation_id、owner、epoch、租约和剩余额度。
- 事务和谁一起提交：预留是一笔原子事务，锁定这条任务的预算。结算是另一笔原子事务，按 call_id 幂等入账。不和 Checkpoint 一起提交。
- 进程退出后任务还在不在：已提交的累计还在。进程退出不把预算清零，也不把结果未知的预留直接释放。

### 工具闸门

- 负责什么：所有工具调用都经过这里。检查参数、权限、审批、预算、取消和执行权。写操作还要先有已提交的 operation_id。
- 存什么：调用记录关联 task_id、epoch、call_id、operation_id。凭证不写入图状态。
- 核哪个标识：owner、epoch、租约、call_id。写操作再核 operation_id。
- 事务和谁一起提交：闸门不代替 T3。没有已提交的操作账本，不允许发出写调用。预算预留用预算自己的事务。
- 进程退出后任务还在不在：任务和已提交的账本还在。已经发出的调用不因闸门进程退出而当成没发生。

### MCP 出站

- 负责什么：按已登记的工具契约连接外部工具。业务幂等不靠 MCP 的请求 ID。
- 存什么：连接可以丢。不存任务，也不存 operation_id 的权威结果。
- 核哪个标识：工具契约版本和 server_id。外部副作用仍核 operation_id，那是账本的标识。
- 事务和谁一起提交：不和任务事务一起提交。
- 进程退出后任务还在不在：连接断开不取消任务。任务还在。

### 入站 MCP

- 负责什么：按需把外部调用转成现有的受理、查询和取消。不另建一套任务状态机，也不提供改 Checkpoint 的能力。
- 存什么：不存任务副本。
- 核哪个标识：受理核幂等键；查询和取消核 task_id。
- 事务和谁一起提交：受理仍是 T1。
- 进程退出后任务还在不在：连接断开不取消任务。任务还在。

### 上下文与记忆

- 负责什么：按任务固定的输入边界组装模型输入。
- 存什么：会话、摘要和获准记忆在 PostgreSQL。Redis 只放可丢的副本。
- 核哪个标识：conversation_id 管持续对话，task_id 管这一次请求，thread_id 管这一代图状态。三个不混用。消息按 message_id 去重。
- 事务和谁一起提交：先提交 PostgreSQL 里的消息或摘要，再写缓存。
- 进程退出后任务还在不在：已提交的上下文还在。缓存可以没有。任务还在。

### Redis

- 负责什么：可丢弃的热点缓存。
- 存什么：指定修订版的热点消息和摘要，带 TTL。
- 核哪个标识：读取时核修订版和当前权限。不拿缓存核执行权。
- 事务和谁一起提交：不和租约、Checkpoint、操作账本一起提交。
- 进程退出后任务还在不在：缓存可以空。任务还在。不能用缓存恢复任务。

### 对象存储与 Artifact

- 负责什么：放大附件和大型工具输出。
- 存什么：对象、版本、摘要和权限。PostgreSQL 只存引用。
- 核哪个标识：对象键、版本和权限。不核 epoch 来决定对象是否存在。
- 事务和谁一起提交：上传完成并校验权限之后，才在 PostgreSQL 事务里提交引用。
- 进程退出后任务还在不在：引用已经提交，任务还在。没写入 PostgreSQL 的临时对象不是持久结果。

### Milvus

- 负责什么：知识或长期记忆的向量索引。
- 存什么：可重建的索引。不存任务执行记录。
- 核哪个标识：检索时核租户、权限和原文版本。不核 epoch。
- 事务和谁一起提交：不和任务事务一起提交。
- 进程退出后任务还在不在：索引可以重建。任务还在。

### Approval

- 负责什么：人工等待。保存审批摘要、主体、有效期和恢复位置。到期不能代替批准。
- 存什么：等待请求、动作摘要、恢复引用和 interrupt 标识。
- 核哪个标识：等待请求标识和输入版本。恢复执行时再核新的执行权。
- 事务和谁一起提交：进入等待时先保住恢复依据，再释放执行权和槽位。有效输入或审批结果，和恢复用的 Outbox 同事务登记。
- 进程退出后任务还在不在：等待记录已经提交，任务还在，状态仍是等待。进程退出不自动批准，也不自动取消。

### 假写操作

- 负责什么：一门假的写。认 operation_id，并能按这个编号查询结果。用来把接口定下来。
- 存什么：operation_id 和结果，存在 MySQL。不存 Task、epoch、租约和 Checkpoint。
- 核哪个标识：operation_id。同一个编号不写第二次。
- 事务和谁一起提交：T4，MySQL 自己的事务。不和 PostgreSQL 一起提交。
- 进程退出后任务还在不在：假业务进程退出，底座里的任务还在。MySQL 里已经提交的结果还在。结果不明时，Runtime 按原 operation_id 查询，不发起第二笔写。

### 业务图

- 负责什么：领域里的节点、分支和动作意图。真实业务图不进这个仓库。
- 存什么：不存执行权、调度记录和操作账本。
- 核哪个标识：不核 owner 和 epoch。它只提出要更新的状态，由 Runtime 校验后提交。
- 事务和谁一起提交：不直接提交底座事务。
- 进程退出后任务还在不在：图不在这个仓库里。任务仍然可以留在 PostgreSQL。外部副作用由假写操作按 operation_id 定接口。

### Kubernetes 部署

- 负责什么：把接入层、消息投递、Runtime 分成三个部署，并在实例没了的时候补上。不读任务，不读 Checkpoint，不判断业务有没有做完。
- 存什么：不存任务。
- 核哪个标识：不核幂等键、消息 ID、dispatch_seq、epoch、operation_id、call_id。
- 事务和谁一起提交：不参加 T1 到 T6。
- 进程退出后任务还在不在：Pod 退出，已提交的任务还在。任务能不能继续，看 PostgreSQL 里的租约和 Runtime 的恢复扫描，不看 Pod 是否被拉起来。

## 受理到恢复的事务

- T1：接入层写入任务、幂等登记、受理事件、Outbox。成功返回 202。
- 投递：消息投递器把 Outbox 发到 Kafka。这一步和 T1 不是一笔事务。
- T2：Runtime 校验逻辑消费方和消息 ID、dispatch_seq、expected_epoch、租约。接管成功才增加 epoch。
- T3：调用假写之前，Runtime 提交 operation_id 和动作意图。
- T4：假写操作在 MySQL 按 operation_id 写入或返回已有结果。
- T5：Runtime 核对执行权后，提交阶段、任务状态和事件。
- T6：Checkpoint 按 task_id 加 epoch 单独提交图位置。

从 Checkpoint 恢复，只恢复图走到哪。外部动作是否已经发生，查操作账本和假写操作的原编号。
